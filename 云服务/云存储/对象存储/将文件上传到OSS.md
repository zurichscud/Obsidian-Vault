将文件上传到阿里云 OSS 通常有两种架构方案。

## 1. 服务端代理上传

客户端把文件发给服务端，服务端接收后上传至 OSS，适合需要后端做文件校验、图片处理或记录日志的场景。

### 1.1 优势

- **业务集成与同步处理**：后端拿到文件流后，可直接在内存或临时磁盘中完成校验与处理，例如解析 Excel/CSV 并写入数据库、计算哈希查重、图片加水印或转码。文件落库与业务记录更新处于同一调用链路，无需处理异步状态通知。
- **凭证与权限集中**：AccessKey / SecretKey 封装在后端内网，不向客户端暴露；权限控制沿用 Spring Security、JWT、RBAC 等常规机制 。
- **客户端与网络要求低**：前端只需提交标准 `multipart/form-data` 请求，无需引入云厂商 SDK 或编写获取签名的接口；请求仅发往自身业务域名，**无需配置 CORS**。

### 1.2 缺点与架构瓶颈

- **双倍带宽与网络 I/O 阻塞**：数据经过“客户端 → 业务服务器 → 对象存储”两次完整传输，严重挤占业务服务器的上下行带宽，高并发或网络高峰时易导致其他常规 API 响应变慢或超时。
- **硬件资源开销大**：大文件或并发上传时，Web 容器（如 Tomcat）会持续占用内存缓冲、线程连接或临时磁盘文件，可能引发内存泄漏、GC 停顿甚至磁盘空间写满。

## 2. 客户端直传（高并发/主流推荐）

服务端生成带有效期的预签名上传凭证（STS / PostObject 策略），前端直接上传至 OSS，**不占用服务器带宽与内存**。

### 2.1 优势

- **卸载业务服务器压力**：业务服务器仅负责计算并下发几十字节的签名 JSON，文件传输完全由对象存储的服务器带宽承载，避免应用服务器的带宽拥塞与 CPU/内存耗尽。
- **延迟更低、速度更快**：文件从终端直达最近的云服务节点或边缘加速节点；海量并发上传（如短视频、相册备份、大型设计稿）时，不易出现业务网关排队堆积与超时断联。
- **原生支持大文件分片与断点续传**：配合云厂商的前端 SDK（如 `ali-oss`），可在浏览器或客户端内计算分片、并行上传并持久化断点状态；网络中断恢复后只需补传未完成的切片，无需重建服务端长连接。
- **安全鉴权细粒度、强隔离**：凭证全程保留在服务端，前端不接触核心密钥；通过 Policy 或 STS 下发的凭证具备强时效性、严格目录隔离（仅限指定用户前缀目录）以及体积/文件类型限制。

### 2.2 缺点与限制

- **业务状态同步更复杂**：文件直接存入对象存储，业务后端无法天然感知文件何时上传成功。必须配置 OSS 的上传回调（Callback），由 OSS 通过 Webhook 异步通知业务服务器更新数据库；或者由客户端在上传完成后二次调用后端接口上报状态，但这种方式存在客户端掉线导致“孤儿文件”的风险。
- **跨域安全（CORS）配置**：前端通过浏览器直接向不同域名的 OSS Bucket 发起请求，必须在云控制台准确配置 CORS 规则。
- **无法在内存中同步预处理**：如果业务逻辑需要在写入前对文件做强校验、解析或修改（例如即时解析 Excel 内容入库、提取特定元数据等），直传无法在服务端内存流中完成拦截，需额外借助云厂商的无服务器函数进行后置处理。
- **客户端实现复杂度上升**：客户端不再只是提交单个 POST 表单，而是需要处理“获取签名 → 执行直传  → 确认回调”的完整链路。
