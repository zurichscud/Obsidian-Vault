## 1. npm v2

### 1.1 依赖结构

依赖目录采用纯树形、递归嵌套的结构，`package-a` 与 `package-b` 各自嵌套一份 `package-c@1.0.0`：

```text
node_modules/
├── package-a/
│   └── node_modules/
│       └── package-c@1.0.0
└── package-b/
    └── node_modules/
        └── package-c@1.0.0
```

### 1.2 特点

- **结构清晰直观**：每个包的依赖完全属于自己，隔离彻底。

### 1.3 致命缺陷

- **深度嵌套与路径过长**：在 Windows 系统上很容易触发 260 字符的文件路径长度上限（MAX_PATH 限制），导致无法读取或删除目录。
- **大量重复拷贝**：如果多个包依赖同一个 `package-c@1.0.0`，它会在每个子目录里重复下载并拷贝一份，造成极大的磁盘浪费与缓慢的安装速度。

## 2. npm v3

npm v3 为了解决 npm v2 的路径过长和重复冗余问题，引入了依赖提升（Hoisting）机制。

### 2.1 依赖结构

将次级依赖尽可能“提升”到根目录的 `node_modules` 下，**只有版本冲突时才嵌套**：

```text
node_modules/
├── package-a/
├── package-b/
├── package-c@1.0.0   <-- 提升到顶层共享
└── package-d/
    └── node_modules/
        └── package-c@2.0.0  <-- 版本冲突时才嵌套
```

### 2.2 解决的问题

- 扁平化消除了多层深度嵌套，避开了 Windows 路径长度限制。
- 相同版本的依赖在顶层只保留一份，减少了重复安装。

### 2.3 带来的新问题

- **幽灵依赖**：因为所有依赖被提升到顶层 `node_modules`，开发者在代码中甚至可以直接 `require('package-c')`，即使 `package.json` 中根本没有声明它。一旦直接依赖后续升级或移除了 `package-c`，代码便会隐蔽报错。
- **不确定性**：安装顺序可能影响哪个版本的依赖被提升到顶层（这也是后续 npm v5+ 引入 `package-lock.json` 的原因）。
- **依然存在单工程硬拷贝**：每个不同的本地工程依然需要全量复制一份庞大的 `node_modules`。

## 3. pnpm

pnpm 采用软链接（Symlink）与硬链接（Hardlink），彻底颠覆了前两者的做法。

### 3.1 工作机制

1. **全局统一存储**：所有包无论在多少个项目中被引用，只在磁盘的全局 Store（如 `~/.local/share/pnpm/store`）中下载并存储一份文件。
2. **硬链接**：项目创建时，从全局 Store 通过硬链接直接映射到项目的虚拟存储区（`.pnpm` 目录），不占用额外的物理磁盘空间，安装速度接近秒级。
3. **软链接**：顶层 `node_modules` 下**仅包含 `package.json` 中显式声明的依赖**，其他传递依赖通过软链接隔离在 `.pnpm` 文件夹内。

```text
node_modules/
├── package-a -> .pnpm/package-a@1.0.0/node_modules/package-a
└── .pnpm/
    ├── package-a@1.0.0/
    │   └── node_modules/
    │       ├── package-a/
    │       └── package-c -> ../../package-c@1.0.0/node_modules/package-c
    └── package-c@1.0.0/
```

### 3.2 核心优势

- **杜绝幽灵依赖**：未在 `package.json` 声明的间接依赖无法在业务代码中被直接引入，保障依赖安全性与构建可靠性。
- **极致节省磁盘**：跨项目复用相同版本与相同内容的文件，大幅减少磁盘空间占用。
- **出色的 Monorepo 支持**
