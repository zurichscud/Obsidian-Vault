## 1. 背景：从隐式自动导入回归显式导入

在大型工程化项目和 AI 辅助编程的时代背景下，前端社区正在经历一波从“隐式自动导入”向“显式导入”的回归。

## 2. 为什么越来越多人“反感”自动导入

### 2.1 AI 编程工具的痛点

这是最直接的导火索。

- 现在大家都在用 Cursor、Claude Code 等 AI 写代码。AI 阅读单个文件时，如果文件顶部没有 `import` 语句，它很难第一时间判断 `useUserStore` 或 `formatDate` 来自哪个文件、参数类型是什么，甚至会误以为是全局内置函数，从而改错代码或产生幻觉。
- 显式写出 `import`，相当于直接给 AI 递上一份精确的“文件依赖地图”。

### 2.2 代码可读性与心智负担

- 刚接手一个大型 Nuxt 项目时，代码里突然冒出一个 `useAuth()`，你无法判断它是 Vue 官方的、某个第三方库的，还是项目 `composables/` 目录下自己写的。
- 只能靠 IDE 跳转才能看清来源。在 GitHub 网页端审查 PR 代码时尤其痛苦，因为那里没有 IDE 跳转。

### 2.3 IDE 性能与类型推断延迟

- `unplugin-auto-import` 会在后台动态生成一个巨大的 `.d.ts` 全局声明文件，把成百上千个函数和组件全部塞进全局命名空间。
- 项目一大，TS Server 每次解析和刷新类型都会变慢，偶尔还会出现类型丢失、报错飘红、需要重启 IDE 的情况。

### 2.4 单元测试与代码复用困难

- 如果你想把某个模块抽离成独立包，或者写单元测试（Vitest），依赖全局隐式注入的代码往往需要额外配置 mock 环境。
- 相比之下，显式 `import` 更干净纯粹。
